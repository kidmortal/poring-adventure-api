# Combat, classes and content — diagnosis and plan

A design plan for making the five classes worth playing *together*, and for giving
the game a spine that new bosses, gear and content can be hung off without
rewriting the battle engine each time.

Everything below is measured against what is actually in `src/feature/battle`,
`src/core/prisma/seed/characters.ts` and the schema today — not against how the
systems were meant to feel.

Companion document: `plan.md` (crafting economy). Where the two overlap — food
buffs, in-combat potions — this document takes the combat side and defers the
economy side to that one.

---

## 1. What is already built

The engine is further along than it looks. Parts worth keeping as-is:

| System | Where | State |
|---|---|---|
| Turn-based battle instance, in memory | `BattleInstance`, `battle.ts` | Held in a `battleList`, ticked by cron every 3s |
| Aggro / threat table | `user.aggro`, `getHighestAggroPlayer` | Real threat targeting, decays 20% per damage step |
| Skill categories | `target_enemy`, `target_ally`, `buff_self` | Enough shape for damage, heals, and self-buffs |
| Skill cooldowns and mastery | `LearnedSkill.masteryLevel`, `cooldown` | Multiplier scales with mastery; cooldown ticks per own turn |
| Data-driven buffs with named effects | `Buff.effect`, `effects.ts`, `runEffect` | `power_up`, `parry`, `invincible` — hooks on attack and defence |
| Before/after damage pipeline | `beforeDamageStep` → `startDamageStep` → `afterDamageStep` | The single choke point every hit passes through |
| Enrage timer | `enrageAfterRound`, `BattleUtils.enragedDamage` | Already stops unwinnable fights from running forever |
| Persistent boss health pool | `CurrentGuildBoss`, `GuildBossDamage` | A boss worn down across days, with a damage-ranked payout |
| Party battles | `battle.service.ts` `create` | The whole party is pulled into the fight automatically |

**The `beforeDamageStep`/`runEffect` pair is the most valuable thing in the
codebase for this plan.** It is already an event bus for combat. Almost every
mechanic proposed below is a new entry in the `effects` map rather than new
engine code — that is the property that makes content cheap to add later, and it
should be protected deliberately.

## 2. Why nobody has a reason to group

Nine findings, each verifiable in the code.

### 2.1 There is no defence stat, so a tank cannot tank

`Stats` has `health, mana, attack, str, agi, int`. Damage is applied raw:

```ts
// battle.ts startDamageStep
const randomDmg = Utils.randomDamage(damage.value, 20);
this.damageUser({ user, amount: randomDmg });   // no mitigation, ever
```

A "tank" can therefore only be a bigger health bar. Taking 100 damage with 600
health is arithmetically identical to taking 50 damage with 300 — there is no
role, only a number. Every defensive design decision downstream depends on this
one missing field.

### 2.2 The Knight — the designated tank — has no skills at all

The seed contains skills for Rune Knight (3), Priest (3), Mage (2), Assassin (1),
and **zero for Knight**. A Knight logs in and can press "attack".

### 2.3 Threat is generated by damage, so the tank can never hold it

```ts
// processUserAttack
damage: { value: userDamage, aggro: userDamage }   // aggro === damage
```

Threat *is* damage, one-to-one. The Knight has the lowest attack of any class
(2/level vs the Assassin's 5/level) so the boss will attack the Assassin, always.
The only threat modifier in the game is `power_up`'s `aggro *= 3` — and that
belongs to Rune Knight, not Knight.

The threat table is good code solving a problem nothing can currently use.

### 2.4 `str` and `agi` do nothing outside two skills

`str` is read by Fire Slash. `agi` is read by Backstab. Neither affects turn
order, hit chance, mitigation, or anything else. The Knight's 3 `str` per level —
its largest stat — is dead weight. Turn order is built from array position:

```ts
// battleUtils.ts — interleaves users and monsters by index
for (let i = 0; i < maxLength; i++) { mixedArray.push(users[i].name); ... }
```

An Assassin is not fast. It is just a bigger `attack` number.

### 2.5 Mage and Priest are the same class

Identical per-level blocks: `attack 1, health 2, mana 5, str 1, agi 1, int 3`.
Both scale everything off `int`. The Mage is a Priest that cannot heal. There is
no reason to bring one over the other except the heal, which means there is no
reason to bring a Mage.

### 2.6 Party size makes content easier, never harder

`create` pulls the whole party into a fight against the same single monster, with
its seeded health and attack. Five players kill it five times faster while each
receiving the **full** silver, exp and drop roll — `generateBattleDrops` loops
per user and rolls the whole table for each.

So grouping is already strictly better than soloing, and yet nobody needs a
composition, because nothing in the game is tuned to require one. Coop is
currently a speed bonus, not a design.

### 2.7 Death is not modelled

`damageUser` sets `isDead = true`, and then nothing reads it except
`isPlayersAlive`. `isUserTurn` never checks it: **a dead player keeps taking
turns and keeps attacking.** There is no revive, no penalty, no death mechanic
for a healer to play against.

### 2.8 Resources are not enforced

`processCastTargetEnemy` and friends subtract `manaCost` without ever checking
the balance. Mana goes negative and casting continues. A healer never has to
budget, which removes the single most interesting decision in the healer role.

### 2.9 Buff duration is decremented on the shared `Buff` row

```ts
// decreaseOrRemoveBuffs
user.buffs.forEach(({ buff }) => (buff.duration -= 1));
```

`buff` here is the `Buff` template, not the player's `UserBuff`. In
`processCastBuffSelf` the object pushed is `args.skill.skill.buff` — the same
object hanging off the skill. Cast Power Up twice in a fight and the second cast
is shorter than the first, because the template was mutated. `UserBuff.duration`
is written but never read in battle.

**Smaller bugs worth fixing while in here:**
- `settleBattleAndProcessRewards` sets `this.battleFinished = false` on a path
  where the party has wiped, so a lost battle is never removed — this is what the
  "stuck battles" admin tool exists to clean up.
- Only `monsters[0]` is ever checked for life (`isMonsterAlive`) and it is the
  default target, so multi-monster fights are half-implemented.
- Nothing bounds a player's turn. One AFK party member freezes the fight for
  everyone until someone with authority runs.

## 3. Design principles

1. **The trinity needs three levers, not three names.** Tank = mitigation +
   threat control. Healer = a resource budget under time pressure. DPS = a check
   the party fails if it is too slow. Remove any one and the composition collapses
   into "bring five of the strongest class".
2. **Difficulty must come from mechanics, not from bigger numbers.** A boss that
   just hits harder is beaten with better gear. A boss that cleaves the back line
   is beaten with a tank.
3. **Every new mechanic should be a row in a table plus an entry in `effects.ts`.**
   If adding a boss requires editing `battle.ts`, the pipeline is broken.
4. **Content must have a reason to be repeated and a reason to stop.** Weekly
   lockouts create appointments; endless modes create ceilings. The game needs both.
5. **A player should be able to see why the group won.** Damage, healing and
   damage-taken have to be tracked and shown, or roles feel like a chore rather
   than a contribution.

## 4. The combat core — four changes everything else depends on

These are small, and nothing in sections 5–8 works without them.

### 4.1 Add `defense` and make `str`/`agi` mean something

```prisma
model Stats {
  ...
  defense Int @default(0)   // flat, from class levels + gear
}
model Class {
  ...
  defense Int @default(0)
}
model Item {
  ...
  defense Int?
}
```

Mitigation, applied once in `startDamageStep` so nothing can bypass it:

```ts
// diminishing, never reaches zero damage, no negative-damage edge case
function mitigate(raw: number, defense: number) {
  const reduction = defense / (defense + 50 + 10 * attackerLevel);
  return Math.max(1, Math.floor(raw * (1 - Math.min(reduction, 0.75))));
}
```

The 75% cap is what stops a future gear tier from making a tank immortal — set it
now, before the numbers exist to break it.

Then give the dead stats a job:

| Stat | New meaning | Where |
|---|---|---|
| `str` | +1 attack per 2 points; +0.5 defense per point | derived on stat recalc |
| `agi` | turn order, and evasion at a hard cap of 20% | `generateBattleAttackOrder`, `startDamageStep` |
| `int` | +1 max mana per point; skill scaling as today | derived |

Turn order becomes speed-sorted rather than array-ordered:

```ts
function generateBattleAttackOrder(users, monsters) {
  return [...users.map(u => ({ name: u.name, speed: u.stats.agi })),
          ...monsters.map(m => ({ name: m.name, speed: m.agi ?? m.level }))]
    .sort((a, b) => b.speed - a.speed)
    .map(e => e.name);
}
```

This single change gives the Assassin an identity that is not "bigger number",
and gives `Monster.agi` as a free knob for boss design (a slow boss telegraphs;
a fast boss punishes).

### 4.2 Split threat from damage

Add `threatModifier` to `Skill` (default `1.0`) and stop hard-coding
`aggro: userDamage`:

```ts
aggro: Math.floor(userDamage * (skill?.skill.threatModifier ?? 1))
```

Then the tank kit works on threat, not damage:

| Tool | Shape | Effect |
|---|---|---|
| Taunt | `category: 'taunt'` | Sets caster's aggro to `highestAggro * 1.5`, locks the target for 1 round |
| Defensive stance | `buff_self`, effect `stance` | +50% defence, ×2 threat generation, −30% damage dealt |
| Passive threat | `threatModifier: 2.0` on Knight skills | Holds threat between taunts |

Also raise the aggro decay from `0.8` per damage step to per **round** — decaying
every single hit means a five-player party decays the tank's threat five times
per round, which is why threat feels unstable even before the tank exists.

### 4.3 Enforce resources and model death

- Reject a cast when `mana < manaCost` and push a log line, rather than going
  negative. A healer running dry mid-fight is the entire tension of the role.
- `isUserTurn` returns false for `isDead` players; skip them in the order.
- A dead player stays in the fight, cannot act, and loses their share of the
  drop unless revived. This is what makes a Priest something a party *needs*
  rather than a convenience.
- New skill category `resurrect` for Priest, plus the Alchemy Revive Draught
  from `plan.md` §4 as the party's expensive substitute.

### 4.4 Turn timer

`tickBattle` already runs every 3 seconds and knows whose turn it is. Give a
player turn a 30-second budget; on expiry, auto-attack and advance. This is a
prerequisite for every piece of group content below — a 5-player raid where one
AFK member freezes the instance is unshippable.

## 5. Classes

### 5.1 Fix the roster before adding to it

| Class | Role today | Problem | Fix |
|---|---|---|---|
| Knight | Tank | No skills; lowest attack; `str` inert | Full kit (below); `str` → defence |
| Rune Knight | Off-tank / hybrid | Owns `power_up`, which is the only threat tool | Becomes the *damage* hybrid; threat tools move to Knight |
| Priest | Healer | Works; no mana pressure, no revive | Resource pressure, revive, cleanse |
| Mage | DPS | Identical to Priest | Re-stat and give it a niche (below) |
| Assassin | DPS | One skill; `agi` inert | `agi` → speed; a combo mechanic |

### 5.2 Proposed per-level stat blocks

Differentiated so the archetypes read at a glance:

| Class | atk | hp | mp | str | agi | int | def |
|---|---|---|---|---|---|---|---|
| Knight | 2 | 7 | 1 | 3 | 1 | 1 | **3** |
| Rune Knight | 3 | 5 | 2 | 2 | 2 | 1 | **2** |
| Assassin | 5 | 2 | 2 | 1 | **4** | 1 | 0 |
| Mage | 1 | 2 | 4 | 1 | 1 | **4** | 0 |
| Priest | 1 | 3 | **6** | 1 | 1 | 3 | 1 |

The Mage now out-scales the Priest on damage per `int` and has a shallower mana
pool — a burst class that runs dry, against a healer that must last. That is a
real distinction, and it is two numbers.

### 5.3 Skill kits

**Knight — the missing class.** Every entry is data in the existing seed shape;
`taunt` and `shield_ally` are the only two new `effects.ts` entries.

| Skill | Lv | Category | Effect |
|---|---|---|---|
| Provoke | 1 | `taunt` | Forces the target onto the caster for 1 round |
| Shield Wall | 1 | `buff_self` | `stance`: +50% def, ×2 threat, −30% damage dealt |
| Guardian | 10 | `target_ally` | `shield_ally`: redirects 50% of an ally's damage to the caster for 2 rounds |
| Shield Bash | 15 | `target_enemy` | 150% str damage, `threatModifier: 3` |
| Last Stand | 25 | `buff_self` | Cannot drop below 1 hp for 2 rounds; the raid-saving cooldown |

**Priest additions:** Resurrect (`resurrect`, long cooldown, heavy mana),
Cleanse (`dispel`, removes one debuff), Barrier (`absorb`, a shield that eats a
fixed amount before health). `absorb` also gives the healer something to do
*before* damage lands, which is what makes healing feel skilful rather than
reactive.

**Mage additions:** Meteor (`target_all_enemies`, needs multi-monster to work —
see §2.9), Frost Nova (`slow`, subtracts from the target's speed and so pushes
them later in the order), Arcane Surge (`buff_self`, next spell doubled).
`slow` interacting with the new agi-ordered turn list is a genuinely new verb
that only exists because of §4.1.

**Assassin additions:** Poison Strike (`dot`, damage at the start of the target's
turn), Shadow Step (`buff_self`, +100% agi for a round → extra turns), Execute
(damage scaling with the target's *missing* health). Ties the class to speed and
to finishing, not to raw attack.

**Rune Knight additions:** stays the flexible hybrid — Rune Enchant (`infusion`
on a weapon: party-wide small attack buff), Earth Spike (str/int hybrid damage).
Its value is being able to cover a missing role badly, which is exactly what a
five-class game with parties smaller than five needs.

### 5.4 Adding classes later

The pipeline for a sixth class should be: one row in `CLASSES`, N rows in
`SKILLS`, an entry in `effects.ts` only if it brings a genuinely new verb, plus
a costume asset. Nothing in `battle.ts` should need touching. Candidates that fit
the trinity without duplicating it: **Bard** (party-wide sustained buffs, the
second support that is not a healer), **Ranger** (ranged DPS with a pet that
takes a slot in the turn order), **Necromancer** (summons, damage-over-time).

Adding classes is the *least* urgent item in this document. Five classes that
each do something no other class can beats eight that overlap.

## 6. Bosses as data, not code

The property to protect: a new boss should be seed rows, never engine changes.

### 6.1 Boss mechanics as a table

```prisma
model Monster {
  ...
  agi     Int  @default(0)
  defense Int  @default(0)
  mechanics MonsterMechanic[]
}

/// One scripted behaviour. The engine reads these; it never knows their names.
model MonsterMechanic {
  id        Int    @id @default(autoincrement())
  monster   Monster @relation(fields: [monsterId], references: [id])
  monsterId Int
  /// Matches a handler key in effects.ts — 'cleave', 'summon_adds', 'enrage', ...
  effect    String
  /// When it fires: 'every_n_rounds' | 'health_below' | 'on_death'
  trigger   String
  /// The trigger's argument: n rounds, or a health percentage.
  value     Int
  /// Handler-specific tuning, as JSON.
  params    Json?
}
```

`tickBattle` gains one call — `runMonsterMechanics(this)` — and every boss after
that is a seed file.

### 6.2 The starting mechanic library

Each of these is ~15 lines in `effects.ts`, and each one *requires* a specific
role, which is the point:

| Mechanic | What it does | Role it demands |
|---|---|---|
| `cleave` | Hits the whole party for 40% | Healer |
| `focus_target` | Ignores threat, attacks the lowest-health player | Healer + fast reaction |
| `heavy_blow` | Telegraphed, 300% damage on the highest-threat player | Tank with a cooldown |
| `summon_adds` | Spawns two minions at 50% health | AoE damage (Mage) |
| `enrage` | Already built | Enough DPS |
| `drain` | Heals itself for 20% of the damage it deals | Mitigation, or a race |
| `curse` | Applies a debuff that halves healing | Cleanse (Priest / Antidote) |
| `armor_up` | Gains defence each round unless dispelled | Dispel |
| `execute_phase` | Below 20% health, doubles attack speed | Burst DPS |

A boss is then a composition: *"cleave every 3 rounds, heavy_blow every 4,
summon_adds below 50%, enrage after round 12"* — four rows.

### 6.3 Difficulty tiers

`CurrentGuildBoss` already carries a `difficulty` string and scaled
`health`/`attack`. Generalise that: every instance of group content picks a
difficulty that multiplies health, attack, and the reward table, and — critically
— **adds mechanics** rather than only scaling numbers. Normal has cleave. Hard
adds the curse. Mythic adds the adds. Same boss, three fights.

## 7. Content structures beyond maps

Maps are an infinite, solo-able, uncapped grind (`plan.md` §2.4). Everything below
is capped, scheduled, and built for a group — which is what gives the loot
ladder somewhere to live.

### 7.1 Dungeons with a weekly lockout — *build this first*

The single strongest addition. A fixed sequence of 3–5 encounters ending in a
boss, entered by a party, with rewards claimable **once per week per player**.

```prisma
model Dungeon {
  id            Int    @id @default(autoincrement())
  name          String @unique
  image         String
  requiredLevel Int    @default(1)
  /// 'weekly' | 'daily' — how often the reward resets.
  lockout       String @default("weekly")
  minPartySize  Int    @default(1)
  encounters    DungeonEncounter[]
  rewards       DungeonReward[]
}

model DungeonEncounter {
  id        Int @id @default(autoincrement())
  dungeonId Int
  /// 1-based; the party fights them in order, health carrying over between them.
  order     Int
  monsterId Int
}

model UserDungeonClear {
  id          Int      @id @default(autoincrement())
  userEmail   String
  dungeonId   Int
  clearedAt   DateTime @default(now())
  /// The UTC week key, so the reset is a unique constraint rather than a cron job.
  periodKey   String
  @@unique([userEmail, dungeonId, periodKey])
}
```

Why this shape:

- **Health carries between encounters.** That is what makes a healer's mana a
  real budget and turns the run into a resource-management problem instead of
  five independent fights.
- **The lockout is a unique constraint on a period key**, not a scheduled job.
  Same trick `userStamina` already uses for the daily refill — no cron, no drift.
- **Weekly rewards are the appointment that makes a guild log in on the same
  evening.** This is the strongest social lever in the document.
- Loot from a first clear should be *tokens*, not gear. Tokens buy gear from a
  vendor, so a bad drop-roll week is still progress. `GuildStoreProduct` and
  `guildTokens` already prove the pattern in this codebase.

Bonus rewards for a full composition — "cleared with a tank, a healer and three
others: +25% tokens" — are two lines of code and the most direct possible push
towards grouping.

### 7.2 Endless Tower

An infinite ladder of floors with a personal best. The cheapest content per unit
of design work in the game, because it is generated rather than authored.

- Floor `n` draws a monster from the pool with `health × (1 + n × 0.15)` and
  `attack × (1 + n × 0.1)`, and gains one mechanic from §6.2 every 5 floors.
- Health and mana **do not** restore between floors. Consumables (`plan.md` §4)
  and a healer become the reason anyone gets past floor 20 — this is the single
  best demand engine for Alchemy in the game.
- A weekly reset, a per-player and per-guild leaderboard, and rewards keyed to
  the **highest floor reached this week**.
- Every 10th floor is a checkpoint you may restart from; floors above your best
  are worth more.

```prisma
model TowerRun {
  id           Int      @id @default(autoincrement())
  userEmail    String
  periodKey    String
  highestFloor Int      @default(0)
  currentFloor Int      @default(1)
  active       Boolean  @default(true)
  @@unique([userEmail, periodKey])
}
```

The tower is where a well-geared player goes when the dungeon is on lockout, and
the leaderboard is what makes gear and composition legible to the whole server.

### 7.3 Raids — the guild boss, generalised

`CurrentGuildBoss` is already 80% of a raid: a persistent health pool, per-member
daily entries, damage-ranked payouts. What it is missing is a reason to bring a
composition, and §4 plus §6 supply exactly that. Concretely:

- Raise the party cap for guild-boss fights above the normal party size.
- Give the boss real mechanics rather than only `enrage`.
- Rank on **contribution**, not damage alone: a `healing` and `damage_taken`
  counter next to `GuildBossDamage.dealtDamage` so a Priest can top a chart.
  Without this, no healer will ever fight a guild boss again once rankings are
  visible, and the role dies at the top end.

### 7.4 Smaller structures, in priority order

| Idea | Shape | Why it earns its place |
|---|---|---|
| **World boss** | Server-wide, appears on a schedule, everyone online can join, loot by contribution | Makes the server feel populated; costs almost nothing on top of the guild boss code |
| **Daily quests** | 3 rotating: kill N on a map, clear a dungeon, tower floor N | The habit loop, and a silver faucet for the non-crafter |
| **Affix rotation** | A weekly modifier on all dungeons (`Fortified`: +30% monster health; `Bolstering`: adds heal each other) | Free content — the same dungeon plays differently every week |
| **Arena / duels** | Async or turn-based PvP against a party snapshot | High engagement, high tuning cost. **Recommend deferring** until the trinity is stable |
| **Solo trials** | A per-class scripted fight with a cosmetic reward | Gives soloists a ceiling that does not require a group |

### 7.5 The reward ladder

Sources should not compete. Each tier feeds the next:

```
Maps (uncapped, solo)      → materials, silver, levelling gear
Daily quests (capped)      → silver, tokens
Dungeons (weekly lockout)  → dungeon tokens → tier gear
Endless Tower (weekly)     → tower tokens → utility gear, cosmetics
Guild boss (daily entry)   → guild tokens → guild store (already built)
World boss (scheduled)     → rare materials for crafters
```

Note the crafting hooks: world-boss materials and enhancement stones are how
`plan.md`'s professions plug into group content. A raid that consumes crafted
food and potions and produces materials only crafters can use is the loop that
makes both halves of the game need each other.

## 8. Making contribution visible

Add three counters to `BattleInstance` next to the existing `damageDealt`:
`healingDone`, `damageTaken`, `threatHeld`. Ship them in `toJson()` and show an
end-of-fight summary.

This is a small change with an outsized effect: it is what tells a player that
being the Knight mattered, and it is a prerequisite for §7.3's contribution
ranking. Roles that cannot be measured do not get played.

## 9. Staged rollout

Ordered by value per unit of work. Each phase is shippable and testable on its own.

### Phase 1 — Make the trinity possible (small, blocking everything else)
- Add `defense` to `Stats`, `Class`, `Item`; apply `mitigate()` in `startDamageStep`.
- `str` → attack/defence, `agi` → turn order and evasion, `int` → mana.
- Split `threatModifier` out of damage; decay aggro per round, not per hit.
- Enforce mana costs; block dead players from acting; fix the `Buff.duration`
  mutation and the stuck-battle path in `settleBattleAndProcessRewards`.

*Outcome: a tank can hold threat and survive; a healer has a budget.*

### Phase 2 — Class identity
- Knight's five-skill kit; `taunt`, `stance`, `shield_ally` in `effects.ts`.
- Priest: Resurrect, Cleanse, Barrier (`absorb`).
- Mage re-stat + Frost Nova / Arcane Surge; Assassin `dot` + Shadow Step.
- Contribution counters and the end-of-fight summary (§8).

*Outcome: five classes that each do something the others cannot.*

### Phase 3 — Bosses as data
- `MonsterMechanic` table, `runMonsterMechanics` in the tick.
- The starting mechanic library (§6.2).
- Multi-monster fights finished properly (targeting, life checks, `summon_adds`).

*Outcome: a new boss is a seed file. This is the phase that makes everything
after it cheap.*

### Phase 4 — Group content
- Dungeons with weekly lockouts; token vendor; full-composition bonus.
- Endless Tower with a weekly leaderboard.
- Guild boss upgraded to real mechanics and contribution ranking.

*Outcome: a weekly appointment, a ceiling to chase, and a reason to have a guild.*

### Phase 5 — Breadth
- World boss, daily quests, weekly affixes.
- A sixth class, if and only if the five feel distinct by then.

## 10. Numbers to settle before building

1. **How lethal should a boss be?** A monster at level 50 currently hits for 35
   against a player with several hundred health. Group content needs a boss that
   can kill an unhealed party in roughly 4 rounds — that is a ~10× jump in boss
   attack, and it must land in the same release as `defense` or every existing
   fight becomes unwinnable overnight.
2. **Party size cap.** Dungeons at 3 (tank/healer/dps) are far easier to fill
   than at 5, and a small server cannot fill 5. My recommendation: **3 for
   dungeons, up to 5 for raids.**
3. **Should map battles cost stamina?** `plan.md` §2.4 argues yes. From the
   combat side the answer is the same, but I would put the cap on *dungeon and
   tower entries* rather than on ordinary grinding — capping the fun part is
   safer than capping the levelling part.
4. **Do dungeon rewards drop gear or only tokens?** Tokens are kinder and easier
   to tune. Gear is more exciting. Suggested: tokens always, plus a small direct
   drop chance for the boss.
5. **Weekly reset timing.** Pick a UTC hour now and put it in one constant — the
   period key computation will end up in three places otherwise.

## 11. What to watch after shipping

- **Class distribution.** If Knights and Priests together are under ~30% of
  characters, the tank and healer kits are still not fun enough — no amount of
  content requiring them will fix that, and forcing the requirement will just
  stop parties from forming.
- **Percentage of fights taken in a party**, before and after dungeons ship.
- **Median dungeon clear time and wipe rate.** A wipe rate near zero means the
  mechanics are decorative; above ~40% means the tuning is out ahead of the gear.
- **Highest tower floor distribution.** A sharp cliff at one floor identifies
  exactly which mechanic is undertuned or unfair.
- **Whether healers ever appear in guild boss rankings** once §7.3 lands. If not,
  the contribution formula is still damage in disguise.

## Appendix — one-line summary of the diagnosis

Coop does not happen because **there is no defence stat, so a tank is only a
health bar; threat is generated by damage, so the tank can never hold it; the
Knight has no skills at all; the Mage is a Priest without a heal; death and mana
are not enforced, so a healer has nothing to play against; and nothing in the
game is tuned to need a composition.** Phase 1 is a few hundred lines and makes
every subsequent phase possible.
